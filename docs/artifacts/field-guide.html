Orientation

The shape of the system

A request crosses four participants: the LWC the user operates, the Apex service layer (LibraryService) it calls, the Open Library API that service consults as a peer, and the Salesforce data store with the trigger that keeps inventory honest. No layer reaches past its neighbor — the LWC never queries data directly, and the trigger never talks to a component.

Layer 1

Data model

Two custom objects carry the state; a message channel and a named credential carry the plumbing.

  • Library_Book__c — Name (the real, editable title), Title__c (a formula = Name), Author__c, Available_Copies__c, Total_Copies__c.
  • Library_Book_Loan__c — Borrower__c (lookup Contact), Book__c (lookup Library_Book__c), Loan_Start_Date__c, Loan_End_Date__c.
  • LibraryRefresh__c — a Lightning Message Channel, fields source and bookId; the sync mechanism between the four components (see Patterns).
  • Open_Library — a legacy Named Credential, Anonymous principal, NoAuthentication protocol, pointed at https://openlibrary.org.
Why a formula field for the title? Every SOQL/SOSL query and the UI reference Title__c for readability and consistency with the challenge brief's field name — but there's nothing to write to on insert except the standard Name field, so Title__c just mirrors it.
Layer 2

Trigger & handler

LibraryBookLoanTrigger runs on after insert and after delete and does nothing but route to LibraryBookLoanTriggerHandler. The handler is fully bulkified: one aggregation, one FOR UPDATE SOQL, one DML — no matter how many loans are in the batch.

The shared aggregator

countLoansByBook turns Trigger.new / Trigger.old into a Map<Id, Integer> — book Id to how many loans touch it in this batch. Three loans for the same book become one entry with count 3, which is what lets both handlers do their work in a single pass instead of once per record.

On insert: validate, then decide per book

if (book == null || available < requested) {
    unfulfillableBookIds.add(bookId);
} else {
    book.Available_Copies__c = available - requested;
    booksToUpdate.add(book);
}
// ...for every loan whose book landed in unfulfillableBookIds:
loan.addError(new NoAvailableCopiesException(
    String.format(NO_COPIES_MESSAGE, new List<Object>{ bookName })
));
addError, not throw. A throw would fail the whole transaction and, on the standard record-creation page, surface a raw Class.X: line N stack panel. addError blocks only the offending Library_Book_Loan__c record — a bulk insert still commits the loans for books that do have stock — and the UI shows just the message.

handleAfterDelete is the mirror image: aggregate, query FOR UPDATE, add the released count back to Available_Copies__c (treating null as 0), one update.

Layer 3

Apex service layer

Three classes, one job each: LibraryService is what the LWCs call; OpenLibraryService is the only class that ever leaves the org; LibraryListController is a thin read-only feed for the two list components.

searchBooks — merge local + external

for (Library_Book__c book : findLocalBooks(searchTerm)) {
    rows.add(new BookSearchResult(book));
    localTitleKeys.add(normalizeTitle(book.Title__c));
}
List<OpenLibraryService.ExternalBook> externalBooks =
    OpenLibraryService.search(searchTerm);
Map<String, Library_Book__c> backfillByTitleKey =
    booksByExactTitle(externalBooks, localTitleKeys);

for (OpenLibraryService.ExternalBook external : externalBooks) {
    String key = normalizeTitle(external.title);
    if (localTitleKeys.contains(key)) { continue; }          // already local
    if (backfillByTitleKey.containsKey(key)) {
        rows.add(new BookSearchResult(backfillByTitleKey.get(key)));
        continue;                                             // just imported
    }
    rows.add(new BookSearchResult(external.title, external.author));
}

booksByExactTitle is a SOQL WHERE Name IN (...) run only for external titles the SOSL FIND didn't already return. It exists because SOSL's index is near-real-time: a book imported seconds earlier can be briefly invisible to FIND, and without this transactionally consistent check it would reappear as an import candidate even though it's already catalogued.

The rest of the class

  • importBook(title, author) — de-dupes by Name, otherwise inserts a book with Total_Copies__c and Available_Copies__c both 1.
  • loanBook(bookId, borrowerId) — selects the book FOR UPDATE, throws NoAvailableCopiesException if copies aren't > 0, otherwise inserts the loan.
  • requestLoan — the @AuraEnabled wrapper; catches everything and rethrows as AuraHandledException, the only exception type whose message reaches the LWC.

OpenLibraryService.search — never throws

A GET to callout:Open_Library/search.json, ten-second timeout. A non-200 status, a CalloutException, or a JSON shape that doesn't parse all just log a WARN and return an empty list — an Open Library outage degrades searchBooks to "local results only," it never breaks the search.

LibraryListController

getBooks() and getRecentLoans() — both @AuraEnabled(cacheable=true), both a single LIMIT 200 query — feed libraryBookList and libraryLoanList through @wire.

Layer 4

Lightning Web Components

All four live on the Home page of a custom DigiLibrary app: libraryBookSearch on top, libraryLoanList and libraryBookList side by side below. libraryLoanButton isn't on the page directly — it renders inside every search result row.

libraryBookSearch

handleTermChange(event) {
    this.term = event.detail.value ?? '';   // typing never searches
}
handleSearch() {
    this.submittedTerm = this.term.trim();  // only this does
    this.runSearch();
}

term (live input) and submittedTerm (what the results represent) are split on purpose: searchBooks performs a callout, so it can't be @wired, and searching on every keystroke would fire one Open Library request per letter. Importing a book is optimistic — markImported flips the row to "local" the instant importBook resolves, before runSearch() reconciles with the server.

libraryLoanButton

One component, two placements. effectiveBookId falls back from bookId to recordId; effectiveBorrowerId falls back from a parent-supplied borrowerId to an internally picked one. showBorrowerPicker is true only when neither borrowerId nor bookId was supplied — that is, only in standalone, record-page use; embedded in a list it just waits for the parent's borrowerId.

libraryBookList & libraryLoanList

libraryBookList is a pure viewer: wire the data, subscribe to LibraryRefresh__c, call refreshApex on a message. libraryLoanList does the same plus a per-row Delete action — LightningConfirm.open, then deleteRecord from lightning/uiRecordApi (no Apex at all), then a toast, a refreshApex, and a publish so the other lists pick up the copy the trigger just returned to the shelf.

Cross-cutting

Patterns that show up more than once

Lightning Message Service is the nervous system

libraryBookSearch and libraryLoanList publish on LibraryRefresh__c after a loan is created, imported, or deleted. All three list-facing components — libraryBookSearch, libraryBookList, libraryLoanList — subscribe and just re-run their own query. No component holds a reference to another.

One exception, two endings

NoAvailableCopiesException is thrown in exactly two places — the trigger handler and loanBook — and each wraps it differently for its audience: addError for the standard-page path, AuraHandledException (via requestLoan) for the LWC path. Same root cause, two UI surfaces, two translations.

SOSL is eventually consistent; SOQL is the fallback

Anywhere a decision has to be correct immediately after a write, SOQL backs up the SOSL index rather than trusting it alone — that's the whole reason booksByExactTitle exists.

Bulkification, everywhere

The trigger handler is 1 SOQL + 1 DML per invocation regardless of batch size; searchBooks and LibraryListController are each exactly one query. No query or DML statement in this codebase sits inside a loop.

Verification

Testing patterns

Apex 38 tests · 99% org-wide Jest 29 tests · ~94% lines

Apex

  • LibraryTestDataFactory / OpenLibraryCalloutMock (@IsTest) build data and stub the HTTP callout with ok / status / rawBody / failing factories.
  • Test.setFixedSearchResults(...) is required before any SOSL runs in a test — without it, FIND always returns empty.
  • Partial success under addError is proven with Database.insert(loans, false) and reading each SaveResult.
  • The one hard-to-reach branch — the trigger's catch (DmlException) fallback — is forced by inserting a title over 80 characters (STRING_TOO_LONG).

Jest

import LightningConfirm from 'lightning/confirm';
// jest.mock('lightning/confirm', ...) is NOT picked up here —
// overwrite the static directly instead:
beforeEach(() => {
    LightningConfirm.open = jest.fn().mockResolvedValue(true);
});

The sfdx-lwc-jest stubs for lightning/messageService and lightning/uiRecordApi already export subscribe, publish, deleteRecord etc. as real jest.fn()s — re-mocking them with a factory is redundant, and for lightning/confirm it silently doesn't take (the module's custom resolver doesn't honor an inline factory the way @salesforce/apex/* imports do), which is why that one gets reassigned instead. Apex wire adapters are stubbed with createApexTestWireAdapter from @salesforce/sfdx-lwc-jest.

Data & trigger

Why is Library_Book__c.Title__c a formula field instead of one you write to?

The real editable title is the standard Name field; Title__c is a formula that mirrors it so SOQL/SOSL and the UI can use a field named after the challenge's spec, while inserts still target Name.

What does countLoansByBook do, and why do both trigger handlers call it?

It aggregates Trigger.new/Trigger.old into a Map<bookId, count>, so N loans for the same book in one batch become one decrement or increment instead of N — it's the bulkification hinge for both directions.

Why addError instead of throw in the handler?

throw fails the whole transaction and shows a raw stack-trace panel on the standard page. addError blocks only the offending loan record, so a bulk insert still commits the loans for books that do have stock.

Service layer

Why can't searchBooks be @AuraEnabled(cacheable=true)?

It performs an HTTP callout through OpenLibraryService, and cacheable Apex methods can't do callouts or DML — the LWC has to call it imperatively instead of through @wire.

What problem does booksByExactTitle solve?

SOSL's search index is only near-real-time, so a book imported moments earlier can be briefly invisible to FIND. The transactional SOQL backfill catches those titles so they show as loanable instead of reappearing as import candidates.

Why does BookSearchResult have two constructors instead of static factories like fromLocal()?

Apex inner classes can't declare static methods.

What's the difference between what loanBook throws and what requestLoan throws?

loanBook throws the real NoAvailableCopiesException for Apex callers and tests. requestLoan wraps every failure in an AuraHandledException, the only type whose message Salesforce actually forwards to the client.

Components

What do effectiveBookId and effectiveBorrowerId do in libraryLoanButton?

They let one component serve two placements — a record page (falls back to recordId) and an embedded search row (uses the explicit values the parent passed) — without the rest of the component caring which context it's in.

When does libraryLoanButton render its own Contact picker?

Only when there's no borrowerId and no bookId — standalone, record-page use. Embedded in a list the parent always passes bookId, so the picker stays hidden and the button just waits for a borrower.

Why does libraryBookSearch keep term and submittedTerm separate?

So typing never triggers a search — only pressing Search or Enter copies term into submittedTerm. searchBooks calls out to Open Library, so searching per keystroke would fire one request per letter.

Who publishes and who subscribes on LibraryRefresh__c?

Publishers: libraryBookSearch (after a loan or import) and libraryLoanList (after a delete). Subscribers: all three list-facing components, including libraryBookSearch itself — it both publishes and subscribes.

Testing

Why is LightningConfirm.open reassigned in tests instead of using jest.mock('lightning/confirm', ...)?

The sfdx-lwc-jest stub ships LightningConfirm as a real class whose static open() throws by design, and its custom module resolver doesn't pick up an inline jest.mock factory for that path the way it does for @salesforce/apex/* imports — so the fix is to overwrite the static method directly on the imported class.

Why doesn't deleting a loan in libraryLoanList need any Apex?

deleteRecord from lightning/uiRecordApi performs the DML through the UI API directly; the after delete trigger fires exactly as it would for any other delete and increments Available_Copies__c.
